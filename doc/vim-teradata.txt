1. INTRODUCTION                                    *vim-teradata-introduction*

vim-teradata is the core Neovim plugin for Teradata SQL development. It runs
queries through Teradata BTEQ, provides on-the-fly diagnostics powered by a
dedicated tree-sitter grammar, and offers schema-aware autocompletion of
databases, tables, and columns.

The plugin is part of a small ecosystem:

    - vim-teradata ........... orchestration, queries, diagnostics
    - tree-sitter-teradata ... Teradata-focused SQL grammar
    - sql-autocomplete ....... metadata-driven completion source

Key features ~

    - Asynchronous query execution via BTEQ
    - Job manager UI for in-flight queries
    - Tree-sitter diagnostics (syntax errors)
    - Schema-aware autocomplete (blink.cmp / nvim-cmp)
    - Query history with optional FZF / Telescope / snacks search
    - Bookmarks (global and per-user)
    - Code actions and node-aware editing
    - Multiple connection profiles backed by `tdwallet`

Target audience: Teradata developers, DBAs, and analysts who know SQL.
Neovim experience is not required.

Non-goals: teaching SQL, generic Teradata setup, non-BTEQ clients.

==============================================================================
2. REQUIREMENTS                                    *vim-teradata-requirements*

Neovim ~
    Minimum:   Neovim 0.12+ (uses `vim.system`, `vim.pack.add`, modern tree-sitter
               and filetype APIs).

Operating systems ~
    Linux, macOS, and Windows (including WSL) are supported. The only
    OS-specific element is the tree-sitter parser library file.

Teradata client ~
    Install the latest Teradata Tools and Utilities (TTU). It provides:
        - `bteq`     -- must be on $PATH
        - `tdwallet` -- for passwordless secure logon
    Confirmed with TTU 20; compatible with 17.10.

Database privileges ~
    For `:TDSync` (metadata refresh), the configured user needs read
    access to `dbc.columnsv`.

Optional dependencies ~
    - A picker plugin: `fzf.lua`, `telescope.nvim`, `snacks.nvim`, or
      `fzf.vim`. Required for |:TDR|.
    - `ripgrep` (`rg`) and `bat` -- required for |:TDR|.
    - `blink.cmp` or `nvim-cmp` for completion UI.

3. INSTALLATION                                    *vim-teradata-installation*

With the built-in `vim.pack` manager (Neovim 0.12+) >lua

    vim.pack.add('ErwonB/vim-teradata')

    require('vim-teradata').setup({
      users = {
        { log_mech = 'TD2', user = 'USER', tdpid = 'HOST' },
      },
    })
<
With `lazy.nvim` >lua

    {
      'ErwonB/vim-teradata',
      ft = { 'sql', 'teradata' },
      opts = {
        users = {
          { log_mech = 'TD2', user = 'USER', tdpid = 'HOST' },
        },
      },
    }
<
With `packer.nvim` >lua

    use({
      'ErwonB/vim-teradata',
      config = function()
        require('vim-teradata').setup({
          users = {
            { log_mech = 'TD2', user = 'USER', tdpid = 'HOST' },
          },
        })
      end,
    })
<
Tree-sitter parser ~

The plugin uses its own dedicated `teradata` tree-sitter parser and does
not replace the default `sql` parser. Install the parser as described in
the online docs at https://teradata-nvim.com/getting-started/treesitter/
then verify with: >

    :checkhealth vim-teradata
<
or: >

    :checkhealth treesitter
<
The output should show that the `teradata` parser is detected.

Metadata sync ~

After installation run |:TDSync| once to build the local catalog index
(databases, tables, columns). Re-run it whenever the schema changes.

4. QUICKSTART                                        *vim-teradata-quickstart*

1. Install the plugin and the Teradata tree-sitter parser.

2. Configure at least one user in your `init.lua`: >lua

    require('vim-teradata').setup({
      users = {
        { log_mech = 'TD2', user = 'USER', tdpid = 'HOST' },
      },
      replacements = { ['${DB_NAME}'] = 'MY_DB' },
    })
<
3. Build the metadata index (one-time / on catalog change): >

    :TDSync
<
4. Open a `.sql` file. Completion becomes schema-aware after `FROM` and
   `JOIN`.

5. Run a query with |:TDO| and watch progress in |:TDJ|.

6. Save useful queries: visually select text, then |:TDBAdd|, and manage
   them with |:TDB|.

Example ~
>sql
    -- placeholder replacement applied before BTEQ
    SELECT *
    FROM ${DB_NAME}.Orders o
    JOIN ${DB_NAME}.OrderItems i
      ON o.OrderId = i.OrderId
    WHERE o.OrderDate >= DATE '2024-01-01'
    QUALIFY ROW_NUMBER() OVER
            (PARTITION BY o.CustomerId ORDER BY o.OrderDate DESC) = 1;
<

5. CONFIGURATION                                  *vim-teradata-configuration*

------------------------------------------------------------------------------
5.1 setup()                                               *vim-teradata-setup*

                                              *teradata.setup()* *:lua-setup*
require('vim-teradata').setup({opts})

    Configures the plugin and creates the filetype association. Must be
    called once during startup (most plugin managers call it for you via
    their `opts`/`config` hook).

    {opts} is a table; all fields are optional except `users`.

------------------------------------------------------------------------------
5.2 Options                                             *vim-teradata-options*

The following keys are accepted by |teradata.setup()|. The values shown
below are the defaults.

                                                      *vim-teradata-opt-users*
users ~
    Type: `table[]`           Default: `{}`

    List of connection profiles. The first profile is the default. Each
    entry is a table with: >lua

        {
          log_mech = 'TD2',   -- logon mechanism (TD2, LDAP, KRB5, ...)
          user     = 'USER',  -- wallet-backed username
          tdpid    = 'HOST',  -- Teradata host or IP
          catalog  = 'NAME',  -- (optional) metadata catalog, defaults to tdpid
        }
<
    catalog (optional)  Name of the metadata catalog. Defaults to `tdpid`.

    Passwords are NEVER stored by vim-teradata. They are retrieved from
    `tdwallet` at logon time using `$tdwallet(<user>)`.

                                               *vim-teradata-opt-replacements*
replacements ~
    Type: `table<string,string>`    Default: `{}`

    String substitutions applied to every query before it is sent to
    BTEQ. Useful for portable scripts: >lua

        replacements = {
          ['${DB_NAME}']  = 'PROD_DB',
          ['${WORK_DB}']  = 'WORK_DB_001',
        }
<
                                                   *vim-teradata-opt-retlimit*
retlimit ~
    Type: `number`            Default: `100`

    Maximum number of rows returned per |:TDO|/|:TDV| query. Controls
    memory and latency.

                                                         *vim-teradata-opt-ft*
ft ~
    Type: `string[]`          Default: `{ "sql", "teradata" }`

    File extensions that activate the Teradata filetype. The plugin
    registers each extension via `vim.filetype.add`. See
    |vim-teradata-filetypes|.

                                                     *vim-teradata-opt-picker*
picker ~
    Type: `string`            Default: `"auto"`

    Picker backend used by |:TDR| and other selection UIs. One of:
        "auto"      detect automatically (tries fzf-lua, snacks, telescope, fzf.vim, native)
        "native"    built-in vim.ui.select (zero external dependencies)
        "fzf_vim"   junegunn/fzf.vim
        "fzf_lua"   ibhagwan/fzf-lua
        "snacks"    folke/snacks.nvim
        "telescope" nvim-telescope/telescope.nvim

                                              *vim-teradata-opt-sql_detection*
sql_detection ~
    Type: `string`            Default: `"always"`

    Controls whether `.sql` files are treated as `teradata`:
        "always"    all `.sql` buffers get filetype `teradata`
        "never"     do not map `.sql` to `teradata`
        "modeline"  inspect first/last 5 lines for 'teradata' or 'bteq'

                                                  *vim-teradata-opt-timeout_ms*
timeout_ms ~
    Type: `number|nil`        Default: `nil` (disabled)

    BTEQ job timeout in milliseconds. Set to nil or 0 to disable timeout.

    In a persistent session (|:TDSession|) the timeout applies to each
    command, counted from the moment it is sent to BTEQ (time spent in
    the queue does not count). A command that times out closes the
    session.

                                                  *vim-teradata-opt-history_max*
history_max ~
    Type: `number|nil`        Default: `nil` (unlimited)

    Maximum number of query history runs kept on disk before pruning.
    Set to nil to disable pruning.

                                                    *vim-teradata-opt-keymaps*
keymaps ~
    Type: `table<string,string|table>`   See |vim-teradata-default-keymaps|

    Normal-mode mappings registered in every Teradata buffer to invoke
    node-aware editing functions ("OPE operations"). Each entry maps a
    key to either:

        - a string: name of an OPE function applied at the cursor node, or
        - a table `{ "func_name", { "node_type", ... } }`: function plus
          the tree-sitter node type to act on around the cursor.

    Example: >lua

        keymaps = {
          ["gcq"] = { "comment_node", { "statement" } },
          ["gdw"] = { "delete_node",  { "where" } },
          ["]s"]  = { "jump_to_next", { "statement" } },
        }
<
    See |vim-teradata-ope| for the full list of available functions and node
    types.

                                                        *vim-teradata-opt-sep*
sep ~
    Type: `string`            Default: `"~"`

    Field separator used in BTEQ result CSV files. Change only if your
    data may contain `~`. Full exports (|:TDExport|) also refuse a `sep`
    containing a single quote or a newline.

                                             *vim-teradata-opt-edit_enabled*
edit_enabled ~
    Type: `boolean`           Default: `true`

    Enables in-grid editing of query results. See
    |vim-teradata-guide-editing|.

                                          *vim-teradata-opt-preview_updates*
preview_updates ~
    Type: `boolean`           Default: `true`

    When true, saving edits opens the generated UPDATE statements in a
    scratch buffer; nothing is sent to BTEQ until you press <CR> there.

                                               *vim-teradata-opt-null_token*
null_token ~
    Type: `string`            Default: `"NULL"`

    Text BTEQ uses to render NULL in result exports (`.set null`). The
    same token typed into a cell in edit mode means SQL NULL. A real
    string equal to the token is indistinguishable from NULL.

                                             *vim-teradata-opt-edit_keymaps*
edit_keymaps ~
    Type: `table`   Default: `{ toggle = "E", save = "S", cancel = "C" }`

    Result-buffer local mappings for edit mode.

                                           *vim-teradata-opt-rerun_keymaps*
rerun_keymaps ~
    Type: `table`   Default: `{ sql = "g.", result = "." }`

    Mappings that re-run the latest query (see |:TDRerun|).

        sql     installed in every Teradata buffer.
        result  installed in every result buffer.

    The two defaults differ on purpose: in a Teradata buffer `.` must keep
    its normal meaning (repeat the last change), so the mnemonic `g.` is
    used instead. A result buffer is 'nofile' and non-modifiable, there is
    no change to repeat, so plain `.` is free there.

    Set either entry to `nil` or `""` to skip that mapping: >lua

        rerun_keymaps = { sql = '<leader>rr', result = '.' }
<
    While a result buffer is in edit mode the mapping refuses to run and
    asks you to save or cancel first.

                                                   *vim-teradata-opt-filter_db*
filter_db ~
    Type: `string|nil`        Default: `nil`

    Optional Lua pattern that limits which database names are imported
    by |:TDSync|. Useful on systems with many irrelevant catalogs.

                                                *vim-teradata-opt-history_dir*
                                              *vim-teradata-opt-bookmarks_dir*
                                                   *vim-teradata-opt-data_dir*
history_dir ~
bookmarks_dir ~
data_dir ~
    Type: `string`

    Paths used for history, bookmarks, and the autocomplete metadata
    cache. Defaults derive from `vim.fn.stdpath('data') .. '/teradata'`.

                                            *vim-teradata-opt-exports_dir_name*
exports_dir_name ~
    Type: `string`            Default: `"exports"`

    Subdirectory of |vim-teradata-opt-history_dir| where full exports are
    written, as `<history_dir>/exports/<id>.csv`. See
    |vim-teradata-guide-export|.

                                                  *vim-teradata-opt-export*
export ~
    Type: `table`

    Full-result export through TPT: the `F` key in result buffers and
    |:TDExport|. See |vim-teradata-guide-export|. Sub-options:

                                          *vim-teradata-opt-export.enabled*
    enabled ~
        Type: `boolean`       Default: `true`

        When false, the `F` key is not bound and |:TDExport| is refused.

                                          *vim-teradata-opt-export.keymap*
    keymap ~
        Type: `string|false`  Default: `"F"`

        Result-buffer key that starts a full export, see
        |vim-teradata-result-mappings|. Set to `false` or `""` to disable
        the key (|:TDExport| still works). Use `"gF"` to keep the `F{char}`
        motion available inside result buffers.

                                          *vim-teradata-opt-export.confirm*
    confirm ~
        Type: `boolean`       Default: `true`

        Show the confirmation box (query id, rows, size estimate, target
        file, operator) before the export starts. `false` starts at once.

                                         *vim-teradata-opt-export.operator*
    operator ~
        Type: `string`        Default: `"auto"`

        TPT operator used for the export:
            "auto"      EXPORT operator on the wrapped query when possible,
                        otherwise SELECTOR (report mode, query unchanged).
                        See |vim-teradata-guide-export|.
            "export"    EXPORT operator only (FastExport protocol). Several
                        sessions, see |vim-teradata-opt-export.max_sessions|.
                        Queries that can't be wrapped are refused.
            "selector"  SELECTOR operator in report mode, query unchanged. A
                        single session. Use it on sites without utility
                        sessions, or to force this route for every query.

                                      *vim-teradata-opt-export.max_sessions*
    max_sessions ~
        Type: `number`        Default: `4`

        Number of sessions for the EXPORT operator. Must be a positive
        integer. Ignored when the query runs with the SELECTOR operator.

                                      *vim-teradata-opt-export.head_lines*
    head_lines ~
        Type: `number|nil`    Default: `nil`

        Number of rows loaded when an export job is opened in a grid from
        |:TDJ| (`<CR>`). `nil` uses |vim-teradata-opt-retlimit|.

                                      *vim-teradata-opt-export.timeout_ms*
    timeout_ms ~
        Type: `number|nil`    Default: `nil`

        Timeout of the TPT process in milliseconds. `nil` or `0` disables
        it. Independent from |vim-teradata-opt-timeout_ms|.

                                      *vim-teradata-opt-export.tpt_script*
    tpt_script ~
        Type: `string|nil`    Default: `nil`

        Path of a TPT script that replaces the bundled one (`export_query`
        or `export_query_selector`, chosen by the route, see
        |vim-teradata-guide-export|).

6. CONNECTIONS                                      *vim-teradata-connections*

Connections are defined in the `users` option (see |vim-teradata-opt-users|).
The first entry is the default. Switch between profiles interactively
with |:TDU|.

Credentials ~
    Passwords live in `tdwallet`. Make sure each `user` configured in
    `vim-teradata` has a matching wallet entry on the host: >

        tdwallet add <USER>
<
    vim-teradata never writes credentials to disk.

Selecting a profile ~
    Run |:TDU|. The list of users opens in a buffer. Mappings:

        <CR>    select user under cursor
        a       add a new user (interactive)
        d       delete user under cursor

The chosen profile is persisted under `history_dir/users.json` so it
survives Neovim restarts.

7. COMMANDS                                            *vim-teradata-commands*

Query execution and editing commands (:TD, :TDO, :TDE, :TDV, :TDM,
:TDMV, :TDF, :TDFF, :TDCodeAction, :TDSession) are buffer-local to
buffers with filetype `teradata` (see |vim-teradata-filetypes|). Global
utilities (:TDH, :TDR, :TDHelp, :TDU, :TDS, :TDB, :TDJ, :TDSync,
:TDRerun, :TDSessions, :TDExport) are available in any buffer.

Several commands accept a count. `[N]` below denotes an optional count
that defaults to 1. For example `:3TDO` runs the statement under the
cursor plus the next two.

------------------------------------------------------------------------------
7.1 Query execution                                   *vim-teradata-cmd-query*

                                                                       *:TD*
:[N]TD          Syntax-check the current statement plus the next N-1
                statements. Statement boundaries are detected via
                tree-sitter, not naive `;` splitting. No execution.

                                                                      *:TDE*
:[range]TDE     Syntax-check the visual selection. The selection is
                split on `;`. Used in visual mode after `:`.

                                                                      *:TDO*
:[N]TDO         Run the current statement plus the next N-1 statements
                via BTEQ and display the results in a split. Honours
                |vim-teradata-opt-retlimit|. See also |:TDExport| to
                export the full result.

                                                                      *:TDV*
:[range]TDV     Run statements of the visual selection (split on `;`)
                and show results. Visual-mode equivalent of |:TDO|.

                                                                 *:TDExport*
:TDExport [id]  Export the full result of the latest output query, or of
                history entry {id}, to a delimited file via TPT (tbuild),
                in the background. A confirmation box is shown first.
                Ids complete from the query history. See
                |vim-teradata-guide-export|.

                                                                      *:TDM*
:[N]TDM         Multistatement run: send the current statement plus the
                next N-1 statements as a SINGLE BTEQ job. Useful for
                transactions and dependent statements. To keep session
                state across separate commands, see |:TDSession|.

                                                                     *:TDMV*
:[range]TDMV    Multistatement run for the visual selection. Splits on
                `;` but submits as one BTEQ job.

                                                                  *:TDRerun*
:TDRerun        Re-run the most recent query, exactly as it was sent. The
                re-run is a new BTEQ job: it gets its own history id and
                its own line in |:TDJ|. Also bound to `g.` in Teradata
                buffers and to `.` in result buffers, see
                |vim-teradata-opt-rerun_keymaps|.

                The refreshed grid replaces the result of the latest query
                wherever that result is on screen: press the key inside
                that buffer, or from the Teradata buffer you ran it from,
                and the same window is reused. If the result window has
                been closed, or you are looking at an OLDER result, the
                new grid opens in its own split, so nothing you are still
                reading is thrown away.

                A query that ran in a persistent session (|:TDSession|) is
                re-run in that same session, so it still sees its volatile
                tables. If that session has been closed, the query runs in
                a one-shot job and a warning is shown.

7.6 Metadata & UI                                      *vim-teradata-cmd-meta*

                                                                   *:TDSync*
:TDSync         Build or refresh the local metadata index used by
                autocomplete. Connects to the active user with TPT and
                writes one catalog per Teradata machine (`tdpid`) under
                |vim-teradata-opt-data_dir|. Users on the same machine
                share a catalog; switching user with |:TDU| switches the
                catalog used by completion and diagnostics. Run |:TDSync|
                once per machine.

                                                                *:TDSync-add*
                                                             *:TDSync-update*
                                                             *:TDSync-delete*
:[range]TDSync[!] add [DB.OBJ ...]
:[range]TDSync[!] update [DB.OBJ ...]
:[range]TDSync delete [DB.OBJ ...]
                Incrementally add, update, or delete one or many objects
                in the local metadata catalog without running a full sync:

                - `add`: fetch the given objects from `DBC.ColumnsV` via TPT
                  and merge them into the local catalog.
                - `update`: same as `add`, and any requested object that no
                  longer exists on the server is removed from the catalog.
                - `delete`: remove the given objects from the local catalog
                  only (synchronous, no server call).

                Target forms:
                - `DB.OBJ [DB.OBJ ...]`: one or more qualified objects
                  (separated by spaces and/or commas; `${VAR}` placeholders
                  are expanded).
                - `DB.*`: whole database (valid for `add`, `update`, and
                  `delete`).
                - No arguments with a visual range (`:'<,'>TDSync add`):
                  object names are read from the visual selection.
                - No arguments without a range (`:TDSync add`): uses the
                  `object_reference` node under the cursor.
                - Single-part name (`:TDSync add vt_name`): registers a
                  session-only volatile/temporary table (not written to
                  disk). By default columns are extracted from the
                  `CREATE VOLATILE TABLE` / `CREATE GLOBAL TEMPORARY TABLE`
                  statement in the current buffer. With `!` (`:TDSync add!
                  vt_name`), a one-shot BTEQ job creates the empty table
                  (`WITH NO DATA`) and runs `HELP COLUMN vt_name.*` on the
                  server. `:TDSync delete vt_name` removes it from the
                  session registry.

                                                                      *:TDU*
:TDU            Open the user manager (see |vim-teradata-connections|).

                                                                      *:TDS*
:TDS            Open the settings manager. Edit `retlimit`, `filter_db`
                and `replacements` interactively.

                                                                   *:TDHelp*
:TDHelp         Open a quick reference of vim-teradata commands in a
                split. Equivalent to a "cheat sheet".

------------------------------------------------------------------------------
7.7 Sessions                                       *vim-teradata-cmd-session*

                                                                 *:TDSession*
:TDSession [open]
                Open a persistent BTEQ session and attach it to the
                current buffer. The session logs on with the active user
                (|:TDU|) and stays logged on until it is closed. While it
                is attached, |:TD|, |:TDE|, |:TDO|, |:TDV|, |:TDM|, |:TDMV|
                and |:TDRerun| run inside it, so volatile tables, session
                query bands, `DATABASE x;` and open transactions carry over
                from one command to the next.
                See |vim-teradata-guide-sessions|.

                                                                *:TDSession!*
:TDSession!
:TDSession close
                Log off and close the session of the current buffer.
                Teradata drops the volatile tables of that session.

:TDSession restart
                Close the session and open a new one. Use it after
                switching user with |:TDU| or changing |vim-teradata-opt-sep|
                or |vim-teradata-opt-null_token|: a session keeps the user
                and settings it was opened with.

:TDSession status
                Show the user, host and state of the current buffer's
                session: `logging on`, `idle` or `busy`, and the number of
                queued commands.

                                                                *:TDSessions*
:TDSessions     List every open session with the buffer it belongs to.

8. MAPPINGS                                            *vim-teradata-mappings*

------------------------------------------------------------------------------
8.1 Buffer mappings                             *vim-teradata-buffer-mappings*

In every Teradata buffer the following mapping is defined:

                                                *vim-teradata-i_CTRL-X_CTRL-U*
i_CTRL-X CTRL-U    Trigger Teradata user-defined completion. Inserts
                   schema-aware completion candidates (databases,
                   tables, columns, functions). The same source is
                   exposed automatically to `blink.cmp` and `nvim-cmp`
                   when they are present.

In addition, the entries of |vim-teradata-opt-keymaps| are installed as
normal-mode mappings buffer-locally. See |vim-teradata-default-keymaps| for
a recommended set.

                                                        *vim-teradata-g_dot*
g.                 Re-run the latest query (|:TDRerun|). In result buffers
                   the same action is bound to `.` instead. Both keys come
                   from |vim-teradata-opt-rerun_keymaps|.

------------------------------------------------------------------------------
8.2 OPE operations                                          *vim-teradata-ope*

"OPE" (Operations on Parse Elements) refers to the suite of node-aware
editing functions exposed by `vim-teradata.td_ope`. They take a
tree-sitter node type as their target and act on the smallest enclosing
node of that type at the cursor.

Available functions ~

    comment_node({type})        Comment out the node (`-- ` prefix per
                                line).
    uncomment_node()            Remove `-- ` prefixes inside the node
                                under the cursor.
    delete_node({type})         Delete the smallest enclosing node of
                                {type}.
    copy_node({type})           Yank the smallest enclosing node of
                                {type} to the unnamed register.
    jump_to_next({type})        Move cursor to the start of the next
                                node of {type} in the buffer.
    jump_to_prev({type})        Move cursor to the start of the previous
                                node of {type} in the buffer.
    format_current_statement()  See |:TDF|.
    format_all_statements()     See |:TDFF|.

Common node types ~

    statement           one complete SQL statement
    select_expression   the SELECT list
    where               the WHERE clause
    term                a single field/expression in a list
    binary_expression   an `a OP b` predicate
    cte                 one entry of a WITH clause

A node type that does not exist at the cursor is a no-op; the operation
emits a warning via |vim.notify()|.

------------------------------------------------------------------------------
8.3 UI buffer mappings                              *vim-teradata-ui-mappings*

Each interactive buffer (|:TDU|, |:TDS|, |:TDB|, |:TDH|, |:TDJ|) defines
its own local mappings. The common idiom is:

    <CR>        accept / open the entry under the cursor
    a           add a new entry
    d           delete the entry under the cursor (with confirmation)
    q           close the buffer

Buffer-specific mappings are shown as virtual text on the last line of
each buffer when it opens.

------------------------------------------------------------------------------
8.4 Result buffer mappings                  *vim-teradata-result-mappings*

Result buffers (|:TDO| / |:TDV| grids) define these mappings on top of the
editing keys (|vim-teradata-guide-editing|) and the re-run key
(|vim-teradata-opt-rerun_keymaps|).

<Tab> / <S-Tab>, <Right> / <Left>
        Move the cursor to the next (`<Tab>`, `<Right>`) or previous
        (`<S-Tab>`, `<Left>`) column on the current row. Accepts a
        `[count]` prefix (e.g. `3<Tab>` jumps 3 columns right).

g0 / g$ Jump to the first (`g0`) or last (`g$`) column on the current row.

<Up> / <Down>
        Sort by the column under the cursor ascending (`<Up>`) or
        descending (`<Down>`). Sorting is cumulative across columns: the
        first sorted column is the primary sort key (`▲1` / `▼1`), the
        second sorted column breaks ties in the first (`▲2` / `▼2`), and
        so on. Pressing `<Up>` or `<Down>` on an already-sorted column
        updates its direction in place at its current sort level.

r       Reset all active column sorts and restore the original row order.

<CR>    Filter rows to those matching the cell value under the cursor.

u       Reset all active filters.

- / <BS>
        Remove the column under the cursor (`-`) or restore the most
        recently removed column (`<BS>`).

                                                        *vim-teradata-result-F*
F       Full export via TPT, after a confirmation box. Exports the full
        result of the query shown in the grid to a file in the background,
        see |vim-teradata-guide-export|.

        `F` shadows the `F{char}` motion (find backwards) inside result
        buffers only. Change the key with |vim-teradata-opt-export.keymap|,
        for example `gF`, or set it to `false` to disable it.

        Not bound on EXPLAIN / SHOW grids and on grids that show an export.
        Refused while the grid is in edit mode: save or cancel first.

9. USER GUIDE                                        *vim-teradata-user-guide*

------------------------------------------------------------------------------
9.1 Running queries                                   *vim-teradata-guide-run*

The two primary commands are |:TDO| (node-based) and |:TDV| (visual).
Both render the result set in a table-formatted split buffer and report
Teradata errors as BTEQ would.

Use |vim-teradata-opt-retlimit| to cap row counts. Very large result sets
(roughly > 10k rows) work but are not the primary use case; for heavy
exports use |:TDExport| (or `F` in the grid), which runs TPT in the
background, see |vim-teradata-guide-export|.

For dependent statements that must share a transaction or session
state, use the multistatement variants |:TDM| / |:TDMV|, or open a
persistent session with |:TDSession| to keep that state between
commands (see |vim-teradata-guide-sessions|).

------------------------------------------------------------------------------
9.2 Diagnostics                               *vim-teradata-guide-diagnostics*

The Teradata tree-sitter parser flags syntax errors as you type. Errors
appear through the standard |vim.diagnostic| interface: virtual text,
signs, |:lopen|, and |vim.diagnostic.get()| all work normally.

Diagnostics refresh on `TextChanged`, `BufEnter`, and `BufWritePost`.

------------------------------------------------------------------------------
9.3 Autocomplete                             *vim-teradata-guide-autocomplete*

After running |:TDSync| once, completion becomes schema-aware:

    - After `FROM ` / `JOIN `: complete databases, then tables.
    - After `<table>.`:       complete columns of that table.
    - Built-in Teradata functions are always suggested.

Completion is exposed as a source to `blink.cmp` and `nvim-cmp`. If
neither is installed, trigger completion manually with `i_CTRL-X CTRL-U`
(see |vim-teradata-buffer-mappings|).

The metadata cache lives under |vim-teradata-opt-data_dir|.
Layout: `<data_dir>/data/<tdpid>/` (one directory per machine). To
separate two users of the same machine, give them different `catalog`
names in |vim-teradata-opt-users|. Re-run |:TDSync|
whenever a DDL change should be visible to the editor.

------------------------------------------------------------------------------
9.4 History                                       *vim-teradata-guide-history*

Every query you run via |:TDO|, |:TDV|, |:TDM|, |:TDMV| is recorded:

    history_dir/queries/<id>.sql
    history_dir/resultsets/<id>.csv

Use |:TDH| to browse, |:TDR| to grep through history (requires a picker).

------------------------------------------------------------------------------
9.5 Bookmarks                                   *vim-teradata-guide-bookmarks*

Bookmarks are named, reusable SQL snippets stored on disk. Two scopes:

    global  shared across all configured users
    user    private to the currently active profile

Add ~
    Visually select a query, then |:TDBAdd|. You will be prompted for a
    name and a scope.

Manage ~
    |:TDB| opens the bookmark manager. Press <CR> to load a bookmark
    into a new split.

------------------------------------------------------------------------------
9.6 Job manager                                      *vim-teradata-guide-jobs*

|:TDJ| opens the Job Manager. It lists every BTEQ job started in the
session with its state (running / done / failed), elapsed time and a
reference to the source query. Press <CR> to jump to the job's log.

Because BTEQ jobs run asynchronously (`vim.system`) you can keep
editing while queries execute and check progress in |:TDJ| anytime.

Jobs that run in a persistent session (|:TDSession|) show `(S)` next to
the user. A session runs one command at a time: a command waiting for
its turn shows `Queued`, then `Running`. Canceling (`x`) a queued
command removes it from the queue; canceling the running command is
described in |vim-teradata-guide-sessions|.

Full exports (|vim-teradata-guide-export|) appear with `operation` set to
`export`. While running they show `TPT running`; when done, the rows
column shows the exported row count. `<CR>` on a finished export opens
the head of the file in a read-only grid, and `d` deletes the export file
(the history query stays).

------------------------------------------------------------------------------
9.7 Code actions                                  *vim-teradata-guide-actions*

|:TDCodeAction| inspects the syntax tree at the cursor and offers
applicable refactorings. Examples (depending on context):

    - Rename alias (renames every occurrence in the enclosing statement)
    - Expand `*` to explicit column list (requires synced metadata)
    - Toggle column qualification with the table alias

Actions are presented through |vim.ui.select()|, so any picker that
hooks into it (telescope, snacks, fzf-lua, dressing.nvim ...) is used
automatically.

------------------------------------------------------------------------------
9.8 Editing results                              *vim-teradata-guide-editing*

Results from |:TDO| / |:TDV| can be edited and written back as UPDATE
statements.

    <E>    toggle edit mode
    <CR>   change the cell under the cursor (in edit mode)
    <X>    set the cell under the cursor to NULL
    <S>    save: generate the UPDATE statements
    <C>    cancel: discard pending changes

Values are changed through a prompt, not by typing over the grid: the
buffer stays read-only and is redrawn from the data after each change.
This keeps column alignment irrelevant - a value containing spaces or a
`|` can never be mis-parsed. Changed cells are highlighted and the hint
line shows how many changes are pending.

Multiple cells on multiple rows can be changed before saving; nothing is
sent to the database until <S>.

Which columns can be edited ~
    Only select items of the form `X`, `a.x`, `a.x AS X` or `a.x X` map
    back to a real column. Everything else (functions, expressions,
    literals, `*`) is dimmed and read-only.

Single-table SELECT ~
    The WHERE clause matches EVERY editable column against its original
    value ("matchall"); NULL originals become `IS NULL`. Since this is
    not a key, several identical rows may be updated - the number of rows
    changed is always reported.

SELECT with joins ~
    Edited columns are traced to their table through the syntax tree, but
    you are asked which columns form the WHERE clause - once per table
    that has edits. The choice is remembered for the buffer.

Not editable ~
    `SELECT *`, DISTINCT, GROUP BY / HAVING, set operations, CTEs,
    derived tables, multistatement results (|:TDM|), EXPLAIN and SHOW.

Results produced in a persistent session ~
    Saving edits (<S>) on a result that came from a persistent session
    runs the UPDATE statements in that same session, so a volatile table
    can be edited too. If the session has been closed, the statements run
    in a one-shot job (which fails for volatile tables).

Failures ~
    The UPDATE statements run in one transaction and stop at the first
    failing statement; the transaction is rolled back and nothing is
    changed.

------------------------------------------------------------------------------
9.9 Editing & formatting                           *vim-teradata-guide-format*

The OPE functions (see |vim-teradata-ope|) let you comment, delete, copy,
and navigate by SQL node type rather than by line. Combined with
|:TDF| / |:TDFF| (experimental formatter) they give you a structured
editing workflow:

    gcq    comment the statement under the cursor
    gdw    delete the WHERE clause
    ]s     jump to the next statement
    :TDF   reformat current statement

9.10 Persistent sessions                       *vim-teradata-guide-sessions*

By default every command starts its own BTEQ process: it logs on, runs
the statement(s), exports the result and logs off. Nothing survives
between two commands. This is what you want most of the time, because
jobs are independent and run in parallel. It rules out anything that
lives in a Teradata session: volatile tables, `SET QUERY_BAND ... FOR
SESSION`, `DATABASE`, `SET SESSION ...`, or a transaction spread over
several commands.

|:TDSession| attaches a long-lived BTEQ process to the current buffer.

Example ~
>sql
    CREATE VOLATILE TABLE vt_orders AS (
        SELECT * FROM ${DB_NAME}.Orders
        WHERE OrderDate >= DATE '2026-01-01'
    ) WITH DATA ON COMMIT PRESERVE ROWS;

    SELECT CustomerId, COUNT(*) FROM vt_orders GROUP BY 1;
<
    :TDSession     open the session (once)
    :TDO           on the CREATE: runs inside the session
    :TDO           on the SELECT: vt_orders is still there

Scope ~
    One session per SQL buffer. Two buffers can each have their own
    session, even with different users. Buffers without a session keep
    the default behaviour.

    A session keeps the user it was opened with: switching user with
    |:TDU| does not affect it (use `:TDSession restart`).

    Result buffers remember the session that produced them: re-running
    (|:TDRerun|, `.`) and saving edits (|vim-teradata-guide-editing|)
    from a result buffer go through that same session.

Ordering ~
    A Teradata session runs one request at a time, so commands sent to a
    session are queued and run in order. |:TDJ| marks them with `(S)`.
    Buffers without a session still run their jobs in parallel.

Lifetime ~
    The session ends with `:TDSession!`, when its buffer is wiped out,
    when Neovim exits, or when the connection is lost. Ending the session
    drops its volatile tables. A lost session is reported with a warning;
    commands then run as one-shot jobs until a new session is opened.

Cancel and timeout ~
    Canceling (|:TDJ| `x`) a queued command just removes it. Canceling
    the running command interrupts it on Linux and macOS and the session
    survives. On Windows the whole session is closed.

    A command that exceeds |vim-teradata-opt-timeout_ms| closes the
    session, because a stuck request cannot be resynchronised.

Statusline ~
    `require('vim-teradata.session').statusline()` returns
    `TD:<user>@<tdpid>` when the current buffer has a session (with a
    trailing `*` while a command runs), and an empty string otherwise: >lua

    vim.o.statusline = "%f %{v:lua.require'vim-teradata.session'.statusline()}"
<
How it works ~
    BTEQ is driven through plain pipes (`vim.system` with an open stdin):
    no terminal emulator and no extra program, the same on Linux, macOS
    and Windows. After each request the plugin sends `.REMARK` markers
    and reads BTEQ's output until the marker comes back. Error messages
    are collected from both standard output and standard error, and are
    shown exactly like for one-shot jobs; everything else BTEQ prints is
    discarded. The session must run in Teradata (BTET) transaction mode,
    like the rest of the plugin.

Caveats ~
    - A statement whose end BTEQ cannot find (missing `;`, unclosed
      `/*`) swallows the markers and the command never completes. Close
      the session, or set |vim-teradata-opt-timeout_ms|.
    - An open transaction (`BT;` without `ET;`) holds its locks until
      you end it or close the session.
    - `.EXPORT`, `.SET` and other BTEQ commands typed in your SQL affect
      the whole session and can interfere with the plugin's own export.

------------------------------------------------------------------------------
9.11 Full exports                                  *vim-teradata-guide-export*

A result grid from |:TDO| / |:TDV| is a preview: BTEQ fetches at most
|vim-teradata-opt-retlimit| rows. To get the whole result, export it. The
export runs the same query through TPT (`tbuild`) in the background and
writes a delimited file; the grid is never loaded with it.

Workflow ~
    1. Run |:TDO|. When the result is truncated, the warning says so and
       mentions `F`.
    2. Press `F` in the grid, or run |:TDExport| (with no argument it
       exports the latest output query; `:TDExport {id}` exports a history
       entry).
    3. A confirmation box shows the query id, the user, the row count (when
       known), a size estimate, the target file, and the operator (the
       route and the reason, see "How the query is sent"). Press
       `y` to start. `n`, `q` or `<Esc>` cancel, and leaving the box cancels
       too. `<CR>` does nothing, so an accidental Enter cannot start it.
       Set |vim-teradata-opt-export.confirm| to `false` to skip the box.
    4. The job appears in |:TDJ| with `operation` `export`. One export per
       query id runs at a time.
    5. When it finishes, press `<CR>` on the job in |:TDJ| to open the first
       rows (|vim-teradata-opt-export.head_lines|) in a read-only grid. A
       hint line shows the row counts and the full file path. Filters and
       sorting in that grid apply to those rows only; open the file itself
       for the full data.

How the query is sent ~
    Route W (EXPORT operator, the default when possible): the query is
    wrapped so that every column becomes text:

        SELECT TRIM(t.c1) AS c1, ..., TRIM(t.cN) AS cN
        FROM (<query>) AS t (c1, ..., cN);

    `TRIM` formats numbers and dates with the column FORMAT, like BTEQ, so
    the export matches the preview. A leading `LOCKING ... FOR ACCESS`
    modifier is moved outside the wrapper. Route W uses the multi-session
    EXPORT operator.

    Route R (SELECTOR operator in report mode, single session, query
    unchanged) is used when the query can't be wrapped: a top-level
    `ORDER BY` (including `TOP n ... ORDER BY` and set operations ending
    with `ORDER BY`), a `WITH` (CTE), an unrecognised `LOCK` form, no
    preview header, the tree-sitter teradata parser unavailable, or
    |vim-teradata-opt-export.operator| set to `selector`. The dialog's
    Operator line shows the route and the reason.

    If a wrapped export fails on a data type (TPT12108, TPT02639, or
    TRIM on BYTE, VARBYTE, LOB, JSON, XML, PERIOD or UDT columns), it is
    retried once automatically in report mode within the same |:TDJ| job,
    with a notification. Setting |vim-teradata-opt-export.operator| to
    `selector` forces report mode from the start.

The query runs twice: once for the preview and once for the export. If
the row count differs between the two, a warning reports it; the data may
have changed in between.

Output format ~
    Files are delimited by |vim-teradata-opt-sep| and not quoted, like the
    BTEQ output. Fields containing the separator break the columns, as
    they do in BTEQ. NULL values are written as empty fields, while the
    BTEQ preview shows |vim-teradata-opt-null_token|. The export grid is
    read-only, so this cannot be mis-edited.

    LOB columns are not supported by the EXPORT operator. Queries with LOB
    columns fail in route W and are retried automatically in report mode
    (see "How the query is sent" above). Set
    |vim-teradata-opt-export.operator| to `selector` to skip the wrapped
    attempt.

Only single SELECT statements can be exported. EXPLAIN, SHOW, DDL, DML
and multistatement results (|:TDM|) are refused with a message.

Persistent sessions ~
    TPT opens its own sessions, so it cannot see what lives in your
    |:TDSession|: volatile tables, `SET QUERY_BAND ... FOR SESSION`,
    `DATABASE` or other session state. The confirmation box shows a warning
    when the query ran in a persistent session. If the query reads a
    volatile or session table, the TPT export is blocked and the box offers
    `[b] Export with BTEQ inside the session` instead of `[y]`. That runs the
    query in the session with no row limit, writes the file, and never loads
    it into a grid. It is slower than TPT.

Cancel and cleanup ~
    `x` on the job in |:TDJ| cancels it. When `twbkill` and `twbrmcp` are
    available, the job is also killed on the Teradata side and its TPT
    checkpoint files are removed. The partial file is deleted. Cancelling
    shows no error.

    `d` on a finished export job deletes its export file after asking for
    confirmation. The history query (`queries/<id>.sql`) is kept, so you
    can export it again.

Files ~
    Export files are written to:

        history_dir/exports/<id>.csv

    The directory name is set by |vim-teradata-opt-exports_dir_name|.
    |:TDJ| and the history pruning (|vim-teradata-opt-history_max|) manage
    these files too.

Errors ~
    On failure the job shows the useful lines of the TPT log. If the TPT job
    id is known, the job also shows a hint to read the full TPT log:

        tlogview -j <jobid> -f '*' -g

    |:checkhealth| vim-teradata reports the TPT script that will be used
    and whether the Teradata Tools and Utilities (`tbuild`, `twbkill`,
    `twbrmcp`, `tlogview`) are found.

Settings ~
    See |vim-teradata-opt-export|. The `F` key is described in
    |vim-teradata-result-mappings|.

11. TROUBLESHOOTING                             *vim-teradata-troubleshooting*

`bteq: command not found` ~
    BTEQ is not on `$PATH`. Install TTU and re-open Neovim from a shell
    where `which bteq` succeeds.

`tdwallet ... no entry` ~
    No password is stored for the configured user. Run >

        tdwallet add <USER>
<
    on the host first, then retry.

No diagnostics or syntax highlighting ~
    The tree-sitter parser is missing. Run: >

        :checkhealth vim-teradata
<
    or: >

        :checkhealth treesitter
<
    and follow the install steps for the parser.

`:TDSync` errors with permission denied on dbc.columnsv ~
    Grant SELECT on `dbc.columnsv` to the user used for sync. This is
    the only database privilege the plugin needs.

Completion returns nothing ~
    1. Confirm a successful |:TDSync| has run for the ACTIVE user's
       machine (`:checkhealth vim-teradata` shows the catalog).
    2. Confirm the catalog directory contains the generated files: >

        :echo stdpath('data') . '/teradata/sql-autocomplete/data'
<
    3. With `blink.cmp` / `nvim-cmp`, verify `td_sql_completion` is in
       the active source list.

`:TDR` does nothing ~
    A picker is missing. Install one of the supported pickers (see
    |vim-teradata-opt-picker|) and either `ripgrep` and `bat`.

A command in a persistent session never finishes ~
    BTEQ is still waiting for the end of the statement (missing `;`,
    unclosed `/*` comment or string). Close the session with
    `:TDSession!` and fix the statement. Setting
    |vim-teradata-opt-timeout_ms| makes such commands fail on their own.

`Object 'vt_xxx' does not exist` after a re-run or an edit ~
    The volatile table lived in a session that has been closed (buffer
    wiped, `:TDSession!`, timeout or lost connection). Open a new session
    with |:TDSession| and create the table again.

`BTEQ session could not log on` ~
    Same causes as a one-shot logon failure: missing `tdwallet` entry,
    wrong `tdpid` or logon mechanism. The message shows BTEQ's own error.

"BTEQ reported an error but printed no message" ~
    The request failed (BTEQ's ERRORCODE was not 0) but BTEQ wrote no
    `*** Failure` / `*** Error` line on either output stream. Run the
    statement once without a session (close it with `:TDSession!`) to
    see BTEQ's full output, and report the case with your TTU version.

12. FAQ                                                     *vim-teradata-faq*

Q: Does vim-teradata store my password? ~
A: No. Authentication goes through `tdwallet`; passwords never touch the
   plugin's data directory.

Q: Can I use vim-teradata with vanilla Vim? ~
A: No. The plugin uses Lua, `vim.system`, `vim.diagnostic`, and the
   built-in tree-sitter API. Neovim 0.12+ is required.

Q: Can I run multiple queries in parallel? ~
A: Yes. Every |:TDO| spawns an independent BTEQ job. Track them with
   |:TDJ|. The exception is a buffer with a persistent session
   (|:TDSession|): its commands run one after the other.

Q: How do I run a `BEGIN TRANSACTION ... COMMIT;` block? ~
A: Use |:TDM| or |:TDMV| so every statement is sent in the same BTEQ
   session, or open a persistent session with |:TDSession| and run the
   statements one by one.

Q: How do I use volatile tables? ~
A: Open a persistent session with |:TDSession|, then create and query
   the tables with the usual commands. See |vim-teradata-guide-sessions|.

Q: Does a persistent session need anything besides BTEQ? ~
A: No. It uses the same `bteq` binary through pipes; no terminal
   emulator or extra tool is needed, on Linux, macOS or Windows.

Q: Why is the formatter marked experimental? ~
A: |:TDF| / |:TDFF| work for common DML/DDL but may reorder comments or
   re-indent unusual constructs. Always diff before committing.

Q: How do I change the connection for a single query? ~
A: Switch active user via |:TDU| before running, then switch back.
